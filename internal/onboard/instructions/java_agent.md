Set up Java Test Optimization in CI for the repository's existing __FRAMEWORK__ Maven command. ddtest runs the local validation afterwards with resume_command.

1. Keep the existing POMs, Maven wrapper, JDK versions, Maven goals, profiles, modules, plugins, JVM options, test arguments, test bodies and matrices. One Maven command runs every framework the build declares; do not split it or filter it by framework.
2. Add `datadog/test-visibility-github-action@v3` after `actions/setup-java`, before each selected Maven test step. Set `languages: java`, `api_key: ${{ secrets.DD_API_KEY }}`__SITE_INPUT__, and an exact `java-tracer-version`, such as `1.67.1`, for every instrumented JDK; never leave it empty or `latest`. The action adds dd-java-agent to `MAVEN_OPTS`: a test step that sets `MAVEN_OPTS` in its own `env` must include `${{ env.MAVEN_OPTS }}` to keep the agent. Do not add `-javaagent` options, download the agent or set `DD_CIVISIBILITY_ENABLED` yourself. Keep CI's Maven goals, such as `install`, unchanged: local validation runs only the test lifecycle and never installs or publishes. Tell the user that CI needs the `DD_API_KEY` secret; local validation does not.
3. Exclude `.testoptimization/` from Git: add `/.testoptimization/` to the repository `.gitignore`.
4. Do not run testdrive, a configuration check, Maven or the tests yourself. Run resume_command once, after the edits above: it validates every discovered configuration and feature in disposable copies and returns the next action. When it returns setup_commands, run them as given, then its resume_command. Finish with its exact next_command and render final_response unchanged; only that coordinator result can certify `COMPLETE LOCALLY`.

If CI also runs JDKs dd-java-agent cannot instrument (early-access builds, Java older than 8), scope the Datadog action to the others with a matrix condition, for example `if: ${{ !contains(matrix.java, '-ea') }}`, using the repository's actual axis name. Their unchanged test commands still run. Report each exclusion and its reason; do not drop matrix rows, guard the tests, change JDK versions or exclude a supported configuration merely to obtain a pass. At least one instrumented consumer is required. Local validation runs on the JDK that runs ddtest; it reports other JDKs in the matrix as not yet validated, for the user to validate with `JAVA_HOME` set to them.

Java setup reference: https://docs.datadoghq.com/tests/setup/java/
