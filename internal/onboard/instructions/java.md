Set up Java Test Optimization for the repository's existing __FRAMEWORK__ Maven or Gradle command.

1. Keep the existing POMs, Maven wrapper, JDK versions, Maven goals, profiles, modules, plugins, JVM options, test arguments, test bodies and matrices. One Maven command runs every framework the build declares; selecting a framework does not filter the suite. Use Maven 3.2.1 or newer.
2. Add `datadog/test-visibility-github-action@v3` after `actions/setup-java`, before each selected Maven or Gradle test step. Set `languages: java`, `api_key: ${{ secrets.DD_API_KEY }}`, `site:` when the organization does not use `datadoghq.com`, and an exact `java-tracer-version`, such as `1.67.1`; local validation uses that release, and a floating one cannot be validated. The action adds dd-java-agent to `MAVEN_OPTS` and `GRADLE_OPTS`: a test step that sets either in its own `env` must include `${{ env.MAVEN_OPTS }}` or `${{ env.GRADLE_OPTS }}` to keep the agent, and a `java-instrumented-build-system` input must include the build tool the test steps run. In a reusable workflow (`on: workflow_call`), every caller must pass the secret: `secrets: inherit`, or `DD_API_KEY: ${{ secrets.DD_API_KEY }}` under the caller's `secrets` with `DD_API_KEY` declared under `on.workflow_call.secrets`; a required secret a caller omits fails that workflow. For JDKs the agent cannot instrument (early-access builds, Java older than 8), scope the action to the others with a matrix condition, for example `if: ${{ !contains(matrix.java, '-ea') }}`, keeping their test steps.
3. Run `ddtest testdrive --framework __FRAMEWORK__ --all --yes` after the edits. It validates every discovered Maven configuration in a disposable copy: native Surefire/Failsafe results without and with the CI-pinned agent, application coverage and the six feature controls. It runs only the test lifecycle up to `verify` and never installs or publishes artifacts. CI rows of another JDK major are validated on the local JDK only as a substitute the user accepts with `--accept-substitute-runtime`; otherwise rerun with `JAVA_HOME` set to that JDK. `--check-only` inventories the configurations without running Maven.
4. Keep `.testoptimization/report.html` and `.testoptimization/testdrive.json`, including on failure, and exclude `.testoptimization/` from Git. Post every `Open report:` link to the user. Run full validation again after edits.
5. Ask a human to create a Datadog API key and add it to the repository as the `DD_API_KEY` secret, without sharing the key itself. Local validation needs no Datadog credentials; actual CI execution and Datadog backend processing remain untested until CI runs.

Coding agents start with `ddtest onboard --agent` instead: it returns these CI setup steps, then hands validation to the coordinator (`testdrive --all --agent --yes`), whose `COMPLETE LOCALLY` result a plain `PASSED` does not provide.

Java setup reference: https://docs.datadoghq.com/tests/setup/java/
