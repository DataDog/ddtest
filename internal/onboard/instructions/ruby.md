Set up Ruby Test Optimization for the repository's existing __FRAMEWORK__ command.

1. Keep the existing Gemfile, lockfile, Ruby versions, bundle exec/binstub/Rake/Rails entry points, test arguments, test bodies/helpers, reporters, coverage settings and required application setup. Install the project's normal dependencies first. In a mixed RSpec/Minitest repository, scope this change to __FRAMEWORK__; validate the other framework separately.
2. Ask a human to connect Datadog and configure the CI secret if needed. Add `datadog/test-visibility-github-action@v3` after `ruby/setup-ruby` and bundle setup, before each selected test step. Set `languages: ruby`, `api_key: ${{ secrets.DD_API_KEY }}`, and an exact `ruby-tracer-version` compatible with every instrumented Ruby. Preserve the original matrix and test steps. The action installs datadog-ci and exports `RUBYOPT=-rbundler/setup -rdatadog/ci/auto_instrument`; merge existing Ruby options instead of overwriting them. Keep custom tracer installation paths visible for separate review.
For a Ruby 2.7 matrix entry, use a compatible RubyGems resolver before bundle/tracer installation: set `rubygems: ${{ matrix.ruby == '2.7' && '3.4.22' || 'default' }}` on `ruby/setup-ruby` (use the actual axis name). RubyGems 3.1 can select a native ffi archive requiring Ruby 3.0 even when the same release's portable source gem supports 2.7. Keep the 2.7 test and instrumentation entry; verify the exact tracer instead of excluding it based only on another host's native dependencies.

3. Run `ddtest testdrive --framework __FRAMEWORK__ --all --check-only --tracer-version <same-exact-release> --yes`. This inventories explicit GitHub Actions commands, including matrix `BUNDLE_GEMFILE: ${{ github.workspace }}/gemfiles/...` paths, and checks the installed bundle without installing gems or executing tests. Numeric Ruby selectors (such as `3.4`) are checked against the resolved tracer and its runtime dependencies using RubyGems requirements across the selector's stable releases. This does not certify CI application bundles, engines or platforms. Tracer releases must match local validation exactly. Head/JRuby/TruffleRuby, ambiguous requirement boundaries, unresolved conditions, custom installs and unrecognized wrappers remain inconclusive. A compatible static check does not prove remote CI execution.
4. Run `ddtest testdrive --framework __FRAMEWORK__ --all --tracer-version <resolved-release> --yes` after final setup edits. Use `--command '<existing test command>'` instead of `--all` to validate one prepared local configuration. Existing bundled datadog-ci is reused, so verify the reported actual release. A missing tracer is installed only in a disposable repository copy; the customer's Gemfile and lockfile are preserved.
5. Inspect native baseline/reporting-only comparisons and each controlled feature result: retries, early flake detection, Test Impact Analysis skipping, quarantine, disabled tests and attempt-to-fix. Check that reporting-only coverage names existing application source files; test-file coverage alone is insufficient. The companion observer retains existing reporters. Probes use the selected command and its loaded configuration; if filters, wrappers or custom reporters prevent collecting controls, the feature stays unvalidated. Existing failures may match across both runs. Missing native results or telemetry cannot count as success.
6. Keep `.testoptimization/report.html` and `.testoptimization/testdrive.json`, including on failure. Exclude `.testoptimization/` from Git and gem packaging. Temporary copies, observers and probes are removed. Run full validation again after edits; a later check-only keeps older execution as historical evidence. Copy testdrive's final response block and absolute report links. Report unresolved checks and unexecuted configurations explicitly. No Datadog credentials are needed for these local checks; actual CI execution and Datadog backend processing remain untested.

To resolve CI runtime blockers, validate each additional engine/runtime separately or explicitly scope the Datadog action to compatible numeric Ruby entries using a matrix condition. For example, `if: matrix.ruby != 'head' && !startsWith(matrix.ruby, 'jruby') && !startsWith(matrix.ruby, 'truffleruby')` excludes those entries from instrumentation while retaining their unchanged test commands. Use the repository's actual axis name. Document each exclusion and its reason; do not drop matrix rows, guard the tests, change Ruby versions or exclude a supported configuration merely to obtain a pass. At least one compatible instrumented consumer is required. Plain Ruby validation reports `PASSED` only when every discovered local command/environment passes its own comparison and controls. For agent coordination, use `--agent --yes` on the full testdrive command, then run its exact `next_command` (`testdrive --report`) and render `final_response` unchanged. Only a current coordinator receipt can certify `COMPLETE LOCALLY`; a plain `PASSED` result cannot. If another Gemfile cannot run on this host, prepare a matching runtime and validate it separately; a focused `--command` can pass selected validation while overall onboarding stays `INCOMPLETE`.
